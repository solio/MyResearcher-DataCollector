## D-009

Date: 2026-09-18  
Decision: Give `mop_up.sh` a round-yield measurement and abort on consecutive barren rounds, instead of relying only on a fixed round budget.  
Reason: The wrapper's premise — "a fresh browser session plus a cooldown gives the next round a new chance" — holds for a transient block but not for a source-side rate cap, because a fresh session does not change our IP or reset a server-side counter. On 2026-09-18 the source cut us off after ~70 detail fetches: round 1 yielded 70 rows, then every one of rounds 2–12 yielded exactly **1** row and halted after two instantaneous `access_block` rejections. `MOPUP_MAX_ROUNDS_REACHED` is indistinguishable whether the 12 rounds yielded 70 rows each or 1 row each, so the wrapper could not tell it had stopped making progress and burned 64 minutes for 81 rows.  
Evidence: `runtime/logs/eastmoney-detail-enrichment.jsonl`, window ≥2026-09-18T03:55:54Z — 119 events = 81 `success`, 25 `access_block`, 12 `fetch_failure`, 1 `manual_verification_resumed`. Per-run breakdown: round 1 `{success:70, access_block:3, fetch_failure:1}` over 03:55:56→04:07:09; each of rounds 2–12 `{success:1, access_block:2, fetch_failure:1}` over a ~3.2-minute window. `access_block` responses take 0.20–0.30s (immediate refusal) while the single success per round takes 1.4–1.8s (real page load). Net 47s/row vs the 6.5s/row baseline measured 2026-09-16.  
Alternatives: Raise `MAX_ROUNDS` (rejected — this failure mode does not resolve with more rounds; it likely worsens the cap); raise `COOLDOWN_SECONDS` to e.g. 600 (rejected as the primary fix — it slows the legitimate transient case and still cannot distinguish capped from unlucky); abort on the *first* block (rejected — the driver halts on the first block by design, so that would make `mop_up.sh` a no-op); yield-based barren abort (chosen).  
Impact: every round now logs `MOPUP_HALTED round=… yield=… barren_streak=…`; `MAX_BARREN_ROUNDS` (2) consecutive rounds at or below `MIN_ROUND_YIELD` (1) end the run with `MOPUP_BARREN` and exit 1. Replaying the real 2026-09-18 log, it stops at round 3 instead of 12, saving ~29 minutes and 36 requests. `ALL_DONE` is checked before the yield logic so a legitimately tiny final round is not misread as barren. The residual 192-row backlog is left for a later run at a lower rate; the README documents the block signature and that more retries are counterproductive.  
Evidence level: `CONFIRMED — measured request-log evidence + replay against the real log`.

## D-010

Date: 2026-09-19  
Decision: Make every backfill run print its own per-day `posts` baseline (`DAYCOUNT BEFORE` / `DAYCOUNT AFTER`) instead of reconciling row deltas against figures quoted from a previous session.  
Reason: Verifying the 2026-09-19 backfill produced an apparent 39-row discrepancy. The run inserted exactly 704 rows (`posts` 85232 → 85936), but the per-day counts I was comparing against — `09-17: 1191`, `09-18: 694`, carried over from a chat summary of the 2026-09-18 run — moved by +7 and +627, i.e. +743. A 39-row gap in a table whose rows are keyed `PRIMARY KEY(source, source_item_id)` and whose day bucket is `substr(published_at,1,10)` can only mean existing rows had their `published_at` rewritten to a different day, so the investigation went looking for a date-rewriting bug that does not exist.  
Evidence: The `posts` table grew by exactly 704 rows, and `created_at` decomposition attributes all 704 to inserts in a single 2026-09-19 batch (`created_at >= '2026-09-19'` returns exactly 704; splitting that batch by **`published_at`** gives 595 dated 09-18 and 109 dated 09-19 — note these are *published* dates, the batch itself is one 2026-09-19 batch, and conflating the two axes is exactly the kind of misreading this decision exists to prevent); a further 1849 rows were touched in-place with `published_at` unchanged (counter refreshes). Reconstructing the post-2026-09-18 state with `WHERE created_at <= '2026-09-18T03:54'` yields `09-17 = 1198`, `09-18 = 726`, after which `726 + 595 = 1321` and `1198 + 0 = 1198` close exactly — the true baselines, and the 39 rows were never real. `published_at` stability was independently checked against the frozen `data/collector.legacy.db` snapshot: 8251 of 8251 common `source_item_id`s matched within 60 seconds and **0** differed. The `DAYCOUNT` output was then added and exercised via `DRIFT_CHECK_ONLY=1` (exit 0); its 30-day window shows the expected weekend troughs (08-22/23 = 105/107, 09-05/06 = 130/98), which is also what makes the 109 rows collected on Saturday 2026-09-19 unremarkable.  
Alternatives: Keep reconciling by hand against the previous run's numbers (rejected — the failure mode is silent and produces phantom bugs, as here); store the baseline in a sidecar file under `runtime/` (rejected — a second artifact that can drift from the database and that nothing forces you to refresh); record only `posts_total` (rejected — it cannot localize *which* day moved, which is the whole question); put it in the run report JSON (rejected — `records_new`/`records_existing`/`records_versioned` are already hardcoded 0 on this path, so a JSON field would inherit the same "is this field live?" ambiguity, whereas the log line is derived by a query the reader can re-run).  
Impact: `backfill_all_stocks.sh` prints `DAYCOUNT BEFORE` right after the drift and coverage checks, and `DAYCOUNT AFTER` before `ALL_DONE` and before both `ALL_DONE_HALTED` paths, so even a halted run records what it wrote. Purely additive: no change to collection, to any stop condition, or to the halting logic; `zsh -n` clean and the smoke path exits 0. The README documents the two `created_at` queries that reconstruct any past run, and states the rule directly: **take deltas from the database, never from memory or a chat summary.**  
Evidence level: `CONFIRMED — full reconciliation closes to the row; published_at stability measured against a frozen snapshot`.

## D-011

Date: 2026-09-19  
Decision: Document that `backfill_coverage.covered_to` is an *optimistic* watermark — "the newest time the walk traversed", not "the newest time actually persisted" — and treat isolated holes below it as expected, rather than changing the walk or the watermark semantics now.  
Reason: Verifying the 2026-09-19 backfill (in response to a challenge about whether the login / ad / captcha interstitials on the visible browser had corrupted the data) turned up a row that contradicted the watermark: 601012 `1774862173` with `published_at = 2026-09-18T10:49:49+08:00` was newly inserted although that stock's pre-run `covered_to` was `2026-09-18T03:48:23Z` (= 11:48:23 Beijing). The mechanism is page granularity: list pages hold ~80 posts ordered by time descending, posts shift down the ordering as new ones arrive, so a post can cross a page boundary between runs. A walk that stops on `existing_coverage_reached` may therefore never read the page containing it, while the watermark still advances past it. The walk also writes whatever page it *does* read, which is why the hole was closed on the next run instead of being reported.  
Evidence: 704 rows inserted 2026-09-19; exactly **1 of 704** (0.14%) had `published_at` earlier than its stock's pre-run watermark, computed by diffing each inserted row against the first `COVERAGE` block in `runtime/logs/backfill-driver-20260919.log`. Independently, the pages themselves were demonstrably fine: all 704 rows had 10-digit ids, `+08:00` ISO timestamps, non-empty authors and `guba.eastmoney.com/news` URLs; zero duplicate ids within the run; id↔time monotonic for 703 of 704 adjacent pairs; and two rows fetched live matched the database on `title`, `published_at` to the second, `author_name` and `stock_code`. The 11 rows whose URL bar code differs from `stock_code` are cross-bar posts (sector peers and a commodity bar), and the apparent `登录/验证/广告` keyword hits were false positives on `安全` in ordinary prose.  
Alternatives: Change the stop condition to persist a page only when fully older than the watermark (rejected here — it would stop the walk earlier and widen holes, since the walk's purpose is to write everything it reads); treat the watermark as "no gaps before T" and backfill defensively (rejected — the measured rate is 0.14% and already self-heals on the next run, so a dedicated sweep would cost far more than it recovers); make `covered_to` conservative by rewinding it to the oldest item of the last page written (deferred — this is the likely correct end state, but it changes a contract other tooling reads, so it needs its own review); document the caveat (chosen).  
Impact: the README now states that a hole below `covered_to` is possible and measured, so a future single-row anomaly is not re-investigated as corruption. No code or contract change; the failing-closed behaviour and all stop reasons are untouched. The separate finding that interstitials cannot corrupt results (payload-based extraction, challenge pages have no `article_list`, and `ChallengeAwareEastmoneyTransport` never auto-solves) is recorded in the README with the arithmetic check that no challenge fired: the 180s window versus a 190s total run whose slowest stock took 51s.  
Evidence level: `CONFIRMED — arithmetic and timestamps from the run log; page-granularity mechanism is a repository fact`.

## D-013

Date: 2026-09-19  
Decision: Adopt the cross-session diff (`scripts/ops/served_vs_stored_diff.py`) as the tool that answers "is the served list complete?", and accept its verdict for 601012 — **collection gap = 0** — while explicitly NOT generalising that verdict to the other 15 stocks yet.  
Reason: A legitimate challenge — "if the site shows a login page, then an ad, then a captcha, and you navigate away before I can clear it, how do you know you collected anything?" — cannot be answered by consistency checks *inside* one session, because a site can serve a crawler a degraded-but-self-consistent page (real titles, contiguous ids, 80 rows/page, `rc=1`, no time gaps). Comparing two anonymous fetches and finding them identical proves only that they are the *same view*, not that the view is complete. An earlier claim that "the data is real, verified" on that basis was an over-assertion by the author and is retracted here. The anchor has to come from outside the judged session: posts an **earlier, different-day** session actually stored, checked against what the site serves **now**.  
Evidence: 601012, window 2026-09-17 09:45:08 → 2026-09-19 22:36:33 (8 pages, 640 rows served, 601 `post_type = 0`), 605 DB rows inside the window. `served-not-stored, post_type == 0` = **0** → no gap. `stored-not-served` = **4** (`1774619784` @ 09-17 23:16:43; `1774637253` @ 09-18 06:39:49; `1774790726` @ 09-18 10:09:40; `1774926884` @ 09-18 11:46:10) and every one redirects `302 -> https://guba.eastmoney.com/error?type=2`, i.e. **the site deleted them**; a 3-id positive control drawn from the served list returned `STILL-LIVE` for all three, so "REMOVED" is a property of the site and not of the probe. Per-day inside the window, stored/served: 09-17 `275/274`, 09-18 `293/290`, 09-19 `37/37`. The newest 601012 row in the DB is `2026-09-19T22:36:33+08:00`, identical to the newest served row to the second. The interstitial concern was also closed structurally by tripping the block for real: the IP-level block returns a 2834-byte page, `<title>身份核实</title>`, `<body><div id="root"></div></body>` + `em_capt.js`/`validate.js`, containing **no** `article_list`, and the project's own functions return `is_access_block_page(...) = True` and `parse_list_page(...) -> GubaParseError: missing embedded article_list` — a blocked page hard-fails; it cannot be silently parsed into "a few posts". The block is not shown on every request (the same anonymous session read ~16 list pages before tripping it), which is why "sometimes there is no captcha" is expected.  
Alternatives: Keep cross-checking two anonymous fetches (rejected — self-falsifying, as it "confirmed" a view that a degraded view would also have confirmed); treat every `stored-not-served` id as proof of shrinkage (rejected — moderation deletion is a legitimate cause and was in fact the cause for all 4 here, so this would have produced a false corruption alarm); accept the earlier 5-page run's `stored-not-served = 3` and `served-not-stored = 44` at face value (rejected — both were artefacts: the 44 were a DB-filter/walk-window mismatch and the 3 silently omitted the 4th because the narrower walk never reached it); extend the script to all 16 stocks in this turn (deferred — the probing itself tripped the IP-level block, so a multi-stock run is not currently measurable; re-run it host by host).  
Impact: `scripts/ops/served_vs_stored_diff.py` now derives its comparison window from the walk instead of a hardcoded date, normalises both timestamp shapes through one `norm()` (the DB's `2026-09-17T09:45:08+08:00` versus the payload's `2026-09-17 09:45:08`; `'T' > ' '`, so a raw string range silently shifts whole days), probes each `stored-not-served` id for the delete redirect, and prints a positive control so a dead probe cannot masquerade as a clean result. The README documents the method, the result table, and both traps. **Still open:** the per-stock verdict for the other 15 codes, and the D-012 question of whether 资讯/转发 (`post_type` 1/20) belong in the corpus at all.  
Evidence level: `CONFIRMED for 601012 — zero gap, all 4 anomalies independently confirmed as site-side deletions; NOT yet measured for the other 15 stocks`.

## D-018

Date: 2026-09-23  
Decision: Capture the detail document from the `response` event by **main-document filtering plus "wherever the browser ended up"**, never by `response.url == requested_url`. Treat "a navigation we cannot capture" as a transport error that **names its cause**, and never re-issue a request whose navigation already committed.  
Reason: The `--detail-referer-from-list` scheme (arm `C`, D-017's sibling) reaches the detail with a scripted in-page navigation, so the response has to be collected from the event because a script navigation returns nothing. The first revision matched it exactly on URL. Every detail that **redirects** then captured nothing — a deleted post answers `302 -> https://guba.eastmoney.com/error?type=2` — which surfaced as a transport error instead of the `detail_not_found` the direct `page.goto` path produces. That difference is not cosmetic: `detail_not_found` is what writes the skip ledger, so an uncaptured redirect means the same dead post is re-requested on **every** future run.  
Evidence: One occurrence in the 2026-09-23 backlog pass, 601012 `1774943244` (1 candidate in 258 requests): the candidate reported a transport failure while the browser had committed `error?type=2`. Reproduced offline rather than against the live source — the source was blocking at the time, so a live deleted post would have proved nothing about the cause: `tests/unit/test_eastmoney_browser_transport.py` now drives `FakeRefererPage(detail_final_url="…/error?type=2")` and asserts the transport returns the error-shell document (which `is_not_found_page` classifies) instead of raising. Three further tests pin the parts that could regress silently: non-document responses are ignored (`resource_type` filter), a page whose final URL matches nothing falls back to the last document rather than to "no response", and a failed navigation's error message names the underlying cause (`{type(exc).__name__}: {exc}`) — the previous wording, "did not yield a response", could not distinguish "captured nothing" from "timed out", which is what made this take an investigation.  
Alternatives: Keep the exact-URL match and let redirected details be transport errors (rejected — it retries deleted posts forever, i.e. it converts a permanent condition into unbounded traffic against the source); match on a URL **prefix** or on the post id (rejected — `error?type=2` carries no id, so the prefix has to be "anything not the list page", which is the chosen rule stated less clearly); fix it mid-run (rejected — each stock runs as its own subprocess and a code change between stocks would make the run non-homogeneous, so the fix landed after the run finished, and this defect is therefore **not** exercised by any production run yet); re-navigate when nothing was captured (rejected — that duplicates a request whenever the navigation did commit, the same class of error this entry is about).  
Impact: `browser_transport.py:_get_after_list_visit` collects main documents, clears them after the list page, and hands `_pick_document` the URL the browser actually committed; `_landed` accepts any non-list commit so a redirected detail does not time out; four unit tests added (all 4 are in the same `unit` file, 259 → 262 tests at the time). The capture path still has no live redirect evidence — that gap is stated in the README rather than papered over.  
Evidence level: `CONFIRMED offline — defect observed once in a production run, mechanism reproduced and fixed under a fixture; the live redirect path is NOT exercised`.
