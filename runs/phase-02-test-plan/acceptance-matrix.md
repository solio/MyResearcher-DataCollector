# Phase 2 Persistence Acceptance Matrix

`Given` is recorded in the Fixture column. Every action is expressed at a
public storage/migration boundary or as direct inspection of the resulting
temporary store. No scenario depends on a private helper name.

| ID | Area | Classification | Contract Requirement | Fixture (Given) | Action | Expected observable result | Evidence Type | Priority |

| PST-008 | RawEvidence / temp and pre-publish crash | MUST | A failure before durable raw publish cannot create committed evidence or false success. | A running synthetic run with fault injection at temporary write, flush/fsync, validation, rename or directory-fsync boundary. | Execute one case per pre-publish failure boundary. | No RawEvidence metadata is committed, no `.partial` path is referenced, the run is not terminal success/no-data, and the checkpoint is unchanged. | PST-009 | Atomicity / SQLite failure after raw publish | MUST | Raw publication may precede SQLite failure, but metadata, observation, failure, checkpoint and terminal state remain transactionally consistent. | A valid final raw file has been published; inject SQLite failure/commit failure while finalizing evidence, observation, failure, checkpoint or terminal status. | Finalize the run once for each transaction failure point. | An unreferenced final raw orphan is allowed. | PST-010 | RawEvidence / referenced corruption | MUST | A missing or hash-mismatched referenced raw file causes hard integrity failure. | A completely committed evidence graph; in one copy delete the referenced body and in another mutate its bytes. | Reopen/read the evidence and run the delivered store integrity check for each copy. | Both copies fail closed with an integrity error; neither returns empty bytes, treats evidence as absent/no-data, nor reports the affected run as successfully readable. | Public read/integrity error + file/hash evidence | P0 |
| PST-011 | Observation / first Eastmoney snapshot | MUST | The first accepted observation is version 1, has sufficient source-required evidence, and preserves source null/time semantics. | One synthetic accepted Eastmoney item supported by successful list and detail responses. | PST-012 | Observation / identical reacquisition and scope | MUST | Same latest canonical facts do not create a new version; new run/evidence and scope associations are append-only/idempotent. | Version 1 exists from `scope A`. A second run observes identical facts from `scope B`; a third association repeats `scope B`. | Persist the two reacquisitions. | No version 2 is created and the historical observation row is byte/value unchanged. New request/evidence/run lineage remains reachable; scopes A and B both exist once, and repeating B creates no duplicate. Logical identity is not split by scope. | Row fingerprint + version count + lineage/scope joins | P2 |
| PST-013 | Observation / drift and reappearance | MUST | Changed facts append versions; reappearing historical facts are a new event, never reuse or overwrite an old row. | Three authorized acquisitions for one logical item carry canonical fact fingerprints `A -> B -> A`. | Persist all three in order and read complete history after reopen. | Versions `1, 2, 3` coexist in order; v2 records drift from the then-latest A and v3 records drift from B. Version 1 is unchanged, no row is updated/deleted, and v3 is not an alias/link reuse of v1. | Immutable row snapshots + ordered history/drift lineage | P0 |
| PST-014 | Attempt lineage / retry success and IDs | MUST | All retry attempts persist; supporting evidence points to the successful attempt; persisted IDs are process-stable. | Caller-supplied run UUID; attempt 1 times out, attempt 2 returns 429, attempt 3 returns success bytes and an accepted observation. | PST-015 | Attempt lineage / retry exhaustion | MUST | Exhaustion remains explicit failure and cannot move a checkpoint. | A prior checkpoint and a run whose complete retry budget fails before any trustworthy collection window is established. | Persist every attempt, retry-exhaustion failure and terminal result. | All attempts and the terminal exhaustion failure remain queryable; terminal status is `COLLECTION_FAILED`, never `NO_NEW_DATA`; no accepted observation is fabricated and the prior checkpoint is unchanged. | SQLite attempt/failure/run/checkpoint graph | P0 |
| PST-016 | Failure lineage / parse or schema failure after body | MUST | An acquired body survives parser/schema failure; failure is not empty/no-data. | HTTP 200 response bytes are durably published, then deterministic parsing/schema validation fails. | Finalize the failure through the public persistence boundary. | RawEvidence and actual attempt lineage remain; an explicit parser/schema failure links to them; no accepted observation exists; terminal status is the appropriate failure/spec-mismatch state, not `NO_NEW_DATA`; checkpoint is unchanged without a valid frontier. | Raw file + evidence/attempt/failure/run/checkpoint joins | P0 |
| PST-017 | Checkpoint / SUCCESS and NO_NEW_DATA | MUST | A proven safe frontier may advance atomically for success or verified no-data; zero observations alone is insufficient. | Prior checkpoint `T0`. A negative control has zero observations but no proven outcome/frontier. | Finalize each case. | A and B atomically commit all required lineage, terminal state, `watermark_after=T2`, checkpoint `T2` and `last_safe_run_id`. | PST-018 | Checkpoint / partial safe prefix | MUST | `PARTIAL_COLLECTION` may advance exactly to a proven contiguous safe prefix. | Prior checkpoint `T0`; all work through `T1` is complete and persisted; unresolved work exists only after `T1`; runtime declares safe frontier `T1`. | Finalize the partial run. | Terminal status remains `PARTIAL_COLLECTION`; required prefix evidence/observations and later failure lineage commit; checkpoint advances atomically from `T0` to exactly `T1`, never beyond it, and records this run as the last safe run. | Ordered fixture proof + SQLite transaction/checkpoint graph | P0 |
| PST-019 | Checkpoint / no valid frontier | MUST | Status alone never authorizes movement, and unsafe terminal states preserve the old checkpoint. | Prior checkpoint `T0`; parameterized cases are: partial with no frontier, collection failed, spec mismatch, and cancelled, each without a valid safe frontier. | Finalize each run with its explicit attempt/failure lineage. | Each terminal/failure state remains observable, but checkpoint and `watermark_after` stay at `T0` (or otherwise express no advancement). | PST-020 | Checkpoint / unresolved-gap crossing | MUST | Persistence rejects a runtime candidate that crosses unresolved eligible work. | Prior checkpoint `T0`; item A is complete at `T1`, item B is unresolved at `T2`, item C is complete at `T3`; runtime candidate is `T3`. | Attempt finalization with the crossing candidate. | Checkpoint movement to `T3` is rejected and the prior checkpoint remains.
