## 用户目标

重新实测 curl 等无需浏览器驱动的程序能否直接请求东方财富股吧，分别回答：

1. 能否获取真实列表，包括后续分页？
2. 能否获取列表对应的真实详情正文？
3. 能否在没有验证码、人工介入或浏览器预热的条件下重复执行，并为后续数据判断和训练增加可用原始数据？

旧模型的判断与 2026-08/09 的历史失败不是本次实测结论。成功率、失败类型、时间、请求方法与响应证据必须可复核。

## 研究范围

- 可编写本目录下的独立、低频、有预算的 HTTP 诊断程序；首选 curl、Python 标准 HTTP 客户端及已安装的普通 HTTP 库。
- 测试生产 SOURCE_SPEC 的公开 HTML 列表与标准帖子详情，严格验证 `article_list` / `post_article`。
- 可读取公开来源页面和脚本，研究其中实际引用的公开、匿名、来源自有 API 或移动页面；候选接口只作为研究证据，不能未经验证改成生产入口。
- 浏览器驱动、已有浏览器会话、浏览器 cookie 导出和人工验证成功均不能算本目标成功。
- 不解验证码，不制造挑战参数，不轮换代理或身份，不伪装 TLS/浏览器指纹；收到真实挑战后停止该路径的重复尝试。可记录普通请求配置和协议差异以诊断行为。
- 不修改 `src/`、冻结契约、当前 SOURCE_SPEC 或生产配置，不写生产数据库，不启动现有批量采集链。

## 证据与判定

- 每次请求记录 UTC 与北京时间、匿名客户端/版本、URL、非秘密参数和请求配置、状态码、最终 URL、耗时、响应字节数、SHA-256、解析/挑战判定和失败理由；保存可重放的响应正文，避免凭据进入日志。
- HTTP 200 不等于成功；有验证码脚本不等于发生挑战；有可解析 payload 也不能直接证明页面没有验证码。
- 列表验证来源返回码、非空结构、帖子 ID、类型、原始发布时间、分页进展和重复/重叠；区分 `f.html` 的发布时间排序与默认路由的回复时间排序。
- 详情优先使用本次真实列表中的 `post_type=0` URL，验证请求 ID、响应 ID、来源、时间和正文结构；不能用标题冒充正文。历史已删除帖子单独分类。
- 先离线校准“正常页含验证码脚本”“真实身份核实壳”“payload 与可见挑战并存”等判定，再发起低频线上实验。不能从无 JavaScript 执行的 HTTP 响应推断绝对不存在动态挑战；报告可观测边界。
- 先验证 1 个列表和 1 个详情；若成功，逐步扩展到至少 2 个股票、分页和若干详情，并作独立进程复测。默认间隔至少 3 秒，总预算至多 40 次来源请求；每条路径遇明确挑战即止，避免重试压力。根据实际结果收缩矩阵；没有执行的配置明确列为未测试。
- 分别给出列表与详情的 `可获取 / 被拦截 / 证据不足`，并区分单次成功、有限重复成功与无人值守长期稳定性。不能由小样本外推安全频率或永久免验证码。
